# Managed Project 接入与恢复分流架构变更提案

状态：DRAFT / MAKER REVIEW REQUIRED。Maker 于 2026-10-23 同意采用分流方案，并确认以下恢复边界：资料冲突或证据不足时先停在草案；只延续可验证历史，必要时由 Maker 确认当前事实后建立明确标记的新起点；修复前保留原文件，失败时尽力恢复原样；首轮只执行已知旧格式与现行项目类型的迁移。这些回复**不等于批准本文全部细化条款、下游计划或实现**。

## 1. 意图与问题

现行 Codex Plugin 已将三个 JSON 作为 Managed Project 的唯一权威集合。先前获批的[项目级协作入口初始化提案](CODEX_PROJECT_AGENT_ENTRY_CHANGE_PROPOSAL.md)解决“首次初始化且根目录缺少 `AGENTS.md`”的问题，但其明确排除已激活项目。随后发现的需求横跨四种不同情形：新建与中途接入的首次激活、已激活项目的 `AGENTS.md` 补齐或对照、旧版项目迁移、权威 JSON 残缺或校验失败后的恢复。它们不能用重新运行 `initialize_project` 或一次自动补齐来处理。

目标是让每个项目都能**逐个**获得适用的协作入口，并在需要时安全进入现行三 JSON 权威模型；同时保留 Maker 对既有文件改动、迁移解释和权威恢复的决定权。成功标准是：每个入口条件有清晰的只读诊断、可审批的操作、失败关闭行为和独立验收证据，不把 `AGENTS.md` 变为第四份权威状态。

## 2. 方案选择

| 方案 | 权衡 | 结论 |
| --- | --- | --- |
| 一个统一的“修复项目”操作 | 入口少，但会混淆非权威 `AGENTS.md` 与三个 JSON 的不同授权、回读和失败语义 | 不采用 |
| 按首次激活、入口补齐、旧版迁移、权威恢复分流，共享只读分类与差异报告 | 操作较多，但每条流程的前置条件、Maker 决定和验收可单独检查 | Maker 已选择，本文据此拟定 |

直接手工改三个 JSON 或用聊天推断缺失字段不符合 Decision 015，不列为可实施方案。分流不是让项目同时运行多个状态系统：迁移完成后仍只有现行三个 JSON 权威。

## 3. 不变边界

1. Decision 015 的唯一 Router、唯一三 JSON 权威集合、`inspect_project` 只读查询、Maker 授权、revision／回读／Receipt 闭合规则不变。任何权威写入只能经新定义并获批的 Kernel MCP 受控流程，不能由 Agent 直接编辑文件。
2. `AGENTS.md` 是 Codex 宿主协作 Artifact。缺失、旧版或与模板不同，不自动使已验证的三 JSON 状态失效；它不进入 State Schema、Receipt 哈希、阶段或 Gate。入口操作须独立报告结果。
3. 不批量扫描并改写所有存量项目；每次由 Maker 指定一个项目。`inspect_project` 和任何只读诊断均不得产生修复副作用。任何项目现有的阶段、Pending Request 与 Receipt 均不因本文自动改变。
4. 不使用 `_V*` 历史规格、旧 Python Runtime 或旧 Markdown 状态作为现行运行权威；旧文档可以是迁移证据，但不能未经核对直接复制成三个 JSON。
5. 原[初始化提案](CODEX_PROJECT_AGENT_ENTRY_CHANGE_PROPOSAL.md)的已批准范围保持有效；本提案是新增范围和必要澄清，不追溯修改其批准记录。现有 Decision 016 与下游草稿在审阅本文后须按新的适用范围修订，不能直接实施。

## 4. 先只读分类，再选择操作

对 Maker 指定的项目，先形成一份可阅读的诊断：记录三个权威文件的存在与验证结果、可用旧版文档和根目录 `AGENTS.md` 的存在／内容差异。分类必须把**权威状态**与**协作入口**当成两个独立维度，而不是仅按文件是否存在推断项目是否“已接入”。只读分类不创建目录、不写文件、不消费请求。

| 权威状态 | 允许进入的流程 | 禁止的捷径 |
| --- | --- | --- |
| 三 JSON 均不存在，且确认是首次接入 | 首次激活；`NEW_PROJECT` 或 `ADOPT_EXISTING` | 不得因已有代码库就跳过激活或假定为新建项目 |
| 三 JSON 全部存在且验证通过 | 已激活项目的协作入口补齐／核对，或正常项目推进 | 不得重跑 `initialize_project`，不得为补 `AGENTS.md` 改写 JSON |
| 只有旧 V1／RC Markdown 权威资料、无现行 JSON | 旧版迁移 | 不得把旧 Markdown 直接当成当前 `state.json` |
| JSON 缺一部分、解析／Schema／Receipt 验证失败，或历史身份有疑点 | 权威恢复评估 | 不得用重新初始化掩盖残缺，不得从聊天补全 |

“三个 JSON 都没有”也可能是先前已激活项目的文件被全部删除。如果 Maker 提供了此前激活的证据、或诊断发现旧权威痕迹，就不能擅自判为首次接入；应先报告身份不确定性，走迁移或恢复评估。目录、链接、不可读文件和并发竞争是文件写入的安全失败条件，不是第五种产品生命周期。

## 5. 四条分流

### 5.1 首次激活：新建与中途接入

`NEW_PROJECT` 与 `ADOPT_EXISTING` 都是首次创建现行三 JSON 的激活模式，使用同一授权和初始化闭合流程。区别在于 `ADOPT_EXISTING` 要先由 Agent 根据既有设计、计划、实现和证据评估当前阶段，Maker 确认项目来源与激活请求；不得把已有代码库误当作 P0 空项目。两种模式的根目录缺少 `AGENTS.md` 时，均按已批准的初始化提案生成并回读当前中文模板。

已有普通 `AGENTS.md` 时，首先保护原文件；输出与当前模板的实质差异（入口、权威、语言、过时指令等）供 Maker 决定保留、局部修订或替换。首次激活的权威流程可按已批准提案返回 `EXISTING_REVIEW_REQUIRED`，但**不能将协作入口宣称为已核对完成**；任何既有文本的修改都需 Maker 另行确认，不能通过模板标记自动覆盖。该差异报告的产生时机与是否需要新增只读调用，由下游 Contract 定义，不得延迟到修改文件之后。

### 5.2 已激活项目：逐个补齐或核对 `AGENTS.md`

权威 JSON 已验证通过时，缺少 `AGENTS.md`（包括激活后被删除）视为入口缺失。Maker 指定项目并明确要求补齐后，专用的受控入口操作从当前插件模板排他创建、回读验证；不改变三个 JSON、revision、Receipt、阶段、Pending Request，也不借用 `initialize_project`。存在普通文件时，先只读比较并向 Maker 提交差异；Maker 决定保留、修订或替换之后，才允许对该文件执行对应操作。对比不得抹掉项目原有的合理专属规则，也不得自动把最新版模板整份覆盖上去。

入口修改需检查操作前文件身份或内容摘要；若 Maker 确认后文件已变化，应重新比较并停止旧操作。文件路径不安全、写入失败或回读不一致时，报告实际残留，不影响已验证的权威状态结论。该流程不要求存量项目一次性补齐。

### 5.3 旧版项目：从历史文档迁移到三 JSON

对于只有 V1／RC Markdown 状态文件，或存在旧版 Project Incubator 指令但尚无现行 JSON 的项目，先汇总原有权威文档的内容、出处、版本和冲突，形成拟生成的 `activation.json`、`state.json`、`latest-receipt.json` 的字段来源与待确认项。不能伪造旧运行时从未产生的 Receipt：新 Receipt 必须记录**本次迁移**的受控写入和 Maker 授权，不能冒充历史变更证据。旧材料不足以确定身份、路由、阶段、Decision 或其他必需字段时，只出迁移草案，不写权威文件。

Maker 审阅并确认迁移解释与受控请求后，由专用 Kernel 迁移流程持久化、回读和验证三个 JSON；成功后旧 Markdown 仅保留历史证据角色，不继续作为并行权威。若已有旧 `AGENTS.md`，另走入口差异与 Maker 确认；“有旧指令”本身不意味着要重建本来有效的 JSON。

首轮可执行迁移只针对本仓库已知的 V1／RC Core Context 布局：`PROJECT_PROFILE.md`、`PROJECT_STATE.md`、`PROJECT_PLAN.md`、`PROJECT_DECISIONS.md`（允许其中个别文件缺失，但必需字段仍须可确认），且旧项目类型能映射到现行 `mod`、`desktop-product` 或 `web-product` 及其有效路由。旧版 `AGENTS.md` 可作为入口差异证据，不能单独充当状态权威或证明项目已激活。未知布局、未知项目类型或无法映射的字段只进入诊断和草案，不执行迁移；下游 Design 须列出版本识别、字段映射与代表性样本，不以文件名相同推定内容可信。

Maker 可以根据可复核的当前 Artifact、Evidence 和自身明确确认，重新确认**当前**项目来源、目标、路由、阶段和应保留的 Decision；每个无法从旧资料直接推出的字段都要标为“当前重新确认”，不能写成“历史已验证”。项目 ID 若没有可信旧资料支撑，不沿用一个猜测出的旧 ID；应在 Maker 确认后分配新 ID，并在迁移证据中说明关联。新 Receipt 只证明迁移当次的持久化，不补造旧 revision 或旧授权。

### 5.4 权威 JSON 残缺或验证失败：证据约束恢复

先报告每个文件的存在、解析／Schema／Receipt 校验情况和可用证据。原始文件保留，不以 `inspect_project`、`prepare_activation` 或入口补齐操作顺便写入。能从可信文件、Receipt、历史记录和 Maker 明确决定形成一致恢复方案时，Maker 审阅差异、字段来源与可能丢失的历史，再授权专用 Kernel 恢复；恢复必须有预期文件摘要或 revision 前置条件、受控持久化、回读和新 Receipt 验证，并保留可审计的原始证据。

旧资料彼此矛盾，或不足以可信还原任一必需字段时，**只提交差异和恢复草案，等待 Maker 确认；确认前不得写入三个权威文件**。Maker 的确认也不能把无法验证的历史说成已经验证；若仍无可信恢复基础，项目保持待恢复状态，不报告正常激活或成功推进。具体备份、Receipt 链与冲突解决策略属于后续 Architecture／Contract 必须明确的内容，不能留给实现时临场猜测。

恢复有两种不同结果，不得在返回中混称：

1. **延续可验证历史。** 如果有可信的先前 Snapshot 及对应 Receipt，可从该验证点恢复同一项目身份和可证明的 revision；本次恢复作为新的受控变更记录。验证点之后无法证明的修改不能悄悄并入“已验证历史”，须另列差异供 Maker 确认。
2. **建立新恢复起点。** 如果无法验证原 revision／Receipt 链，但仍能由现存 Artifact 和 Maker 确认当前必需事实，可以建立明确标记的恢复基线。它不声称延续丢失的 revision 或旧授权；提案规定新基线从 revision 0 起步，并用本次受控恢复 Receipt 证明其创建。若原项目 ID 也无法证实，则分配新 ID 并记录关联线索。原 Pending Request 不自动继承，需在新基线建立后按当前规则重新提出。Maker 批准的是当前事实与建立新起点，不是证明缺失历史真实发生。

执行任何权威迁移或恢复前，必须将现存三个 JSON 的原始字节（包括“该文件原本不存在”的事实）及相关旧文档的内容摘要保存到项目内独立、非权威的恢复证据区，关联本次请求与 Maker 确认。证据区不得被 `inspect_project` 当成第四份权威。写入需逐文件安全持久化与回读；若失败，优先按原始字节恢复操作前状态。若某文件已被外部改变或无法安全回滚，则保留现场、标记恢复未闭合并停止后续状态操作，不能把残留误认为一次成功迁移。恢复证据在 Maker 审阅闭合前不得自动清理；确切目录、并发前置条件和长期保留规则由 Contract／Runtime 定义，但不得省略原状保护与可审计关联。

## 6. 影响、次序与非目标

这是一项跨 Architecture、Design、Contract、Runtime、Plan、Plugin Tool、Router 和验收的变更。先补影响分析与 Architecture Decision，再更新分流设计、输入输出与错误语义、事务和失败恢复规范，最后重写实施及验收计划。现有五项初始化计划和 A01–A09 验收草稿只覆盖首次路径，应标为**待修订、不得实施**；可以保留可复用条目，但新增 `ADOPT_EXISTING`、已激活补齐、差异审阅、旧版迁移与残缺恢复的独立验收。

本提案只解决 Project Incubator 的通用接入与恢复流程；不要求立即迁移或补齐任何真实项目，不批准任何项目的阶段变更，不自动升级插件，不修改 `_V*`。实现仍须经完整下游规格和两份计划的 Maker 批准。
